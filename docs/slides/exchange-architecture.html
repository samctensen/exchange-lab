Embedded Driver and Archive

One authoritative book. Gateways submit work and return results.

The external protocol is JSON over WebSocket. The gRPC gateway and protobuf contract have been removed. A browser or backend can use the same JSON contract without SBE codecs.

IPC uses shared memory on one host. Both Java processes connect to the server-owned Media Driver directory. Archive recordings are persistent files stored outside that disposable directory. The current WebSocket launcher listens on 127.0.0.1:8080/orders.

A gateway on another host would require a configured network transport, such as Aeron UDP. Pointing it at a driver directory cannot extend IPC across machines.

Request ID and order ID have different jobs. The reply carries the request UUID.

PlaceResult reports the remaining quantity of the incoming order. Trade contains incoming and resting order IDs, price, and quantity. A response to the submitter does not itself notify every other participant affected by a trade. A durable event or market-data feed is future work.

One thread mutates the book. Other threads handle I/O.

EngineGateway.submit returns a CompletableFuture. Its Aeron worker eventually completes that future. WebSocketOrderHandler schedules JSON encoding and socket writes back onto the connection’s Netty event loop.

An AgentRunner calls AeronEngineAgent.doWork repeatedly. The engine runner uses BusySpinIdleStrategy, while the gateway worker currently uses SleepingIdleStrategy. One writer makes matching state easier to reason about. The engine chooses an admission order across client sessions.

Offers await recording. Execution follows the recorded FIFO head.

The engine holds one pending reply. If that reply cannot be offered, the current loop pauses further admission and execution.

A larger window allows more outstanding work. Matching still has one writer.

These are defaults, not benchmark results or throughput guarantees. Gateway queue capacity, gateway maximum in-flight requests, and the engine log window are independently configurable.

The WebSocket layer also limits each connection to 32 pending responses and the listener to 128 connections. A response slot remains occupied until its socket write completes.

The global pending-reply behavior matters when introducing multiple gateways. Merely creating separate response publications does not change the engine’s scheduling policy.

The engine chooses one order across client sessions, and ArchiveRequestLog writes that order through one ExclusivePublication. Aeron guarantees ordering within a session. Separate incoming sessions do not provide a single global order on their own.

ArchiveRuntime sets file and catalog sync levels to 2. The engine waits for recorded position before applying a fresh request. Durability depends on the storage stack honoring force operations. This is one local Archive without replication or failover.

Known UUIDs can return a cached response without another append. The recording contains requests. Replay reconstructs the book and the response cache.

Current system

Retries and recovery

Same process

A retry sends the same UUID and command.

RequestStateMachine returns the stored outcome.

A changed command under that UUID produces REQUEST_ID_CONFLICT.

After a restart

Replay recorded requests into a fresh state machine.

Rebuild the book and response cache.

Open live request intake after replay, then extend the recording.

A missing reply means an unknown outcome. The command may already have executed.

Suppose the process stops after recording a request but before returning its reply. Startup replay applies that request. Retrying the same UUID and command returns the original result from the rebuilt cache.

The cache also retains business rejections. This is request-level deduplication under the retained history, not a universal exactly-once delivery guarantee. Cache retention, Archive retention, and snapshots still need a coordinated design.

Recovery does not send old replies. It rebuilds state. A new live retry provides the connection that should receive the recovered outcome.

Sources: RequestStateMachine; ArchiveRequestLog; AeronEngineServer.

Each gateway decodes the shared replies, then matches them against its active request UUIDs.

More gateways would create avoidable decoding and shared delivery pressure.

The current gateway creates a normal subscription on aeron:ipc stream 2. The engine owns one publication for that stream. Each subscriber receives the stream and has its own consumption position.

UUID filtering identifies a logical request. It does not establish an exclusive transport destination. A slow subscriber can constrain a shared IPC publication. The engine’s global pending reply can then stall progress. The current documented deployment runs one gateway instance.

The shared request subscription contains an incoming Image for each gateway request publication. The server maintains a response publication for each source image. It chooses the response publication using the route preserved with that request.

This is the live topology we are working toward. The standalone demo already demonstrates the transport association. Carrying RoutedRequest through the engine is one prerequisite, followed by route registration, publication selection, client setup, and lifecycle handling.

Multiple gateway processes can each serve many WebSocket connections. A response route identifies a gateway's Aeron connection. The request UUID then selects the outstanding request within that gateway, and its future completion reaches the originating socket.

Core distinction

Three identities, three lifetimes

IdentityWhat it namesAfter reconnect
Order IDThe business order to place, match, or cancelThe order keeps its identity
Request UUIDOne logical command and its cached outcomeA retry keeps the same UUID
Image correlation IDThe incoming image used to resolve a return routeA new image supplies a new route ID

A place and a later cancel use different request UUIDs for the same order ID.

Persistent command identity survives. Live connection identity can change.

The request UUID distinguishes a retry from a new command. The order ID refers to the business object. A cancel is a new logical command with its own request UUID.

RoutedRequest.responseCorrelationId holds the server-side Image.correlationId. A response subscription also has a registrationId used during client setup. Aeron links these separate identifiers. Neither replaces the request UUID. The session ID is another Aeron identifier and should not be substituted for the image correlation ID here.

Sources: CommandRequest; RoutedRequest; AeronResponseChannelDemo.

Working demo · target live transport

How a response channel finds its client

At each gateway

  1. Create a response subscription with control-mode=response.
  2. Set the request publication’s response-correlation-id to that subscription’s registrationId().

At the engine

  1. Receive the gateway’s request Image.
  2. Create a response publication with control-mode=response and that image’s correlationId().
  3. Keep the image-to-publication association.

Gateways can share response stream ID 2 while receiving their associated response sessions.

The demo uses IPC, so it omits the UDP control endpoint. The project pins Aeron 1.53.0. The standalone demo exercises two logical clients in one JVM and verifies that each receives only its own echo.

The demo routes using the source Image, without inspecting the A or B text. UUID correlation still matters in the live gateway because it can have several requests in flight on one response connection.

RoutedRequest keeps the return address

record RoutedRequest(
    CommandRequest request,
    long responseCorrelationId) { ... }

CommandRequest

The UUID and command belong in the ordered recording.

Replay needs enough information to reproduce execution and cached results.

responseCorrelationId

The source image ID stays with the request in memory.

Reply delivery needs the connection associated with this arrival.

The wrapper connects what to execute with where to reply now.

The handler obtains (Image) header.context(), decodes the SBE message, and creates a RoutedRequest. In the pinned Aeron version, FragmentAssembler preserves this context when assembling fragmented messages.

Keep request data immutable and avoid retaining Aeron receive buffers after a callback. The wrapper prevents routing information from getting lost while a command waits for recording.

Archive receives routedRequest.request(). Recording live image IDs would not help recovery because those connections may no longer exist.

Waiting for Archive must preserve each request’s return route.

Imagine a request from gateway A followed by one from B in the log window. A global “last sender” field could point at B when A becomes ready to execute. That would send A’s response to B. Keeping the route inside each queued wrapper prevents that mix-up.

Both reply paths must carry the wrapper: the recorded FIFO head and a cached retry. The state machine processes the enclosed CommandRequest. pendingResponseCorrelationId holds the route of the reply waiting to be offered.

Saving the route field alone does not switch delivery. offerPendingReply needs the publication lookup in the next integration step.

Target behavior after integration

A retry can return through a new gateway

1

Gateway A sends u-1 through route 41

The engine records and applies the command, then caches its outcome.

2

The reply is lost to the caller

The caller cannot infer whether the command executed.

3

The caller retries u-1 through gateway B, route 77

The command is identical. This arrival has a different transport route.

4

The engine returns the cached outcome through route 77

The book stays consistent and the currently connected caller gets the result.

Deduplicate by UUID. Route the reply using the connection of that arrival.

41 and 77 are illustrative image correlation IDs. u-1 abbreviates a UUID. The cache stores the command and CommandResponse. It should keep the outcome independent of an old reply publication.

The same idea works after recovery because replay rebuilds the cache. The next live retry supplies the return route.

Keeping the engine healthy when gateways disconnect still requires resource cleanup and a policy for undeliverable replies. This scenario describes target behavior after that integration, not a claim that the current live server already implements it.

Expected effects and remaining work

What the routing change improves

With response-channel integration

Each gateway receives its associated replies.

Gateways avoid decoding unrelated responses.

A retry can use a new route while keeping its UUID.

Reply publications have per-connection lifecycle.

Further design work

The global pending reply still couples engine progress.

Slow or disconnected gateways need bounded handling and cleanup.

Latency and throughput gains need measurement.

Authentication, risk, and replication remain separate work.

Delivery isolation provides the foundation. Scheduling and failure handling determine the next gains.

One response publication per source removes the need for all gateways to consume the same reply publication. The current agent still short-circuits doWork when pendingResponse is present, and its reply timeout fails the agent. Separate publications alone do not fix that scheduling policy.

A future policy must define how long to retain undeliverable replies, when to release routes, and how retries recover outcomes.

Response channels provide routing, not authentication or tenant authorization. Account identity, ownership/risk checks, a durable event feed, retention, snapshots, and replication still need their own designs.

Sources: AeronEngineAgent; Architecture overview; Design implications of per-connection response publications.

Route registration and closure need one clear owner. Aeron callbacks and the engine worker can run in different contexts. Resource creation and mutation must follow an explicit ownership model.

Recall practice · reveal each answer

Check your understanding

offer() returns a positive position. Can matching begin?

For a fresh request, wait until Archive’s recording counter reaches the request’s end position. A successful offer confirms acceptance into Aeron’s publication log.

A request waits in the log window. Where should its route live?

With its RoutedRequest inside PendingLoggedRequest. A global “last sender” value can change while another gateway’s request arrives.

A client reconnects after losing a reply. Which identity stays the same?

The retry keeps the same request UUID and command. Its new incoming image supplies the route for the cached response.

Explain these answers aloud before moving on to publication lookup.

Follow-up: does adding gateways make matching concurrent? No. It increases transport and admission demand, while the engine still applies sequenced commands with one writer.

Follow-up: does disconnecting a WebSocket cancel an accepted command? No. It can still execute. Cancellation is a separate command with its own request UUID.
